## Common UI behavior and component choices

Mantine MCP consulted during planning for Stepper, Chip and form inputs. Use the repo's Mantine 9.8.0 controls with existing Carbon visual language and ShiftBox brand assets; no parallel UI toolkit. Planned components: Tabs/Paper/Stack/Text for structure; Switch/TextInput/NumberInput with `@mantine/form`; Button for Save/Refresh/Retry; read-only Chip for state; Alert for persistent explanation; Progress for capacity; Stepper for real workflow. Existing theme supplies semantic amber; text/icon accompany color.

Chip is normally a selectable checkbox/radio primitive. Use documented read-only behavior and a separately announced status so users are not told clicking a health chip changes state. Label all fields and steps; visible focus, keyboard tab order, input errors linked to fields, first error focus, polite live announcements, and non-color state meaning are required. Preserve drafts across tab switches; never reset user input on background polls. Use explicit grouped save, disable duplicate submission, keep saved/effective state distinct while async activation runs, and show stale-write conflicts with refresh/review. Status polling is bounded and active only while tab/workspace view is relevant, with cancellation on auth change.

No purge/delete cache control, upstream list, credentials editor, push hosting or build-result action is in scope. Manual old-location reclamation remains an operator filesystem procedure with UI instructions; adding an admin action later requires its own contract/permissions/E2E row.
