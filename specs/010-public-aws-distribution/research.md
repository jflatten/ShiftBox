# Research: First Public AWS Distribution

## 1. Ship a native customer CloudFormation stack

**Decision.** Use one standalone versioned YAML template with regional mappings and conditions for foundation, database/setup and active controller. Translate the proven private Terraform topology, keeping that root for demo and internal use. Reuse the full Linux amd64 runtime and bootstrap assets. Render the pinned anonymous GHCR image, PostgreSQL digest, ECS host image and regional AMI descriptors into the template. Keep installation volume and secret references stable across phases.

**Rationale.** Quick-create prepopulates a regional CloudFormation review screen and exposes the template, IAM acknowledgements, stack policy, termination protection and optional initial change-set review. Both console and CLI can use the same bytes. Stable logical IDs, explicit encrypted EBS ownership and retention/update-replacement policies preserve persistent data. Use IAM capabilities matching the actual resources and scope stack execution and setup access separately. Use conventional stack rollback and service stabilization to avoid claiming readiness before PostgreSQL and the controller are healthy.

**Alternatives considered.** Customer Terraform requires tooling and state the operator did not request. A custom provisioning runtime or nested stacks add service and asset dependencies. Keep the existing full controller image and native template.

Sources: [Existing demo/topology guide](../../platform/terraform/aws/README.md), [ECS task image syntax](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/task_definition_parameters_ec2.html), [CloudFormation quick-create](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/cfn-console-create-stacks-quick-create-links.html), [DeletionPolicy](https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-attribute-deletionpolicy.html), [UpdateReplacePolicy](https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-attribute-updatereplacepolicy.html).

## 2. Publish clean regional AMIs and keep deployments encrypted

**Decision.** Reuse the AWS Packer recipe and sealing checks. Add a public build mode in an approved publisher context, using a pinned unencrypted Canonical base and disposable build resources. Build one clean amd64 image, copy to the other three commercial regions, verify all backing snapshots and provenance, then grant public AMI launch permission in each region. Share the AMIs through their launch permissions. Customer and demo encryption settings continue to apply to their own resources.

**Rationale.** AWS requires AMI ownership, allows public sharing per region, and disallows public encrypted AMI backing snapshots. Encryption by default can force encrypted build/copy snapshots, and an existing encrypted snapshot cannot be converted into a clean public artifact by copying it. Validate the publisher's regional settings before building or sharing. Check the scrubbed filesystem and current AWS metadata, preserve source lineage across regional copies and hold public images and supporting snapshots for the release lifetime. Record expiry/deprecation and document what happens when a pinned AMI is unavailable. Check cross-account availability without a private launch grant. The EC2 launch path explicitly creates an encrypted root in the customer account, and the customer template encrypts controller and PostgreSQL storage.

**Alternatives considered.** Copying the encrypted demo AMI cannot satisfy public sharing. Distributing encrypted snapshots with a publisher KMS key adds per-account grants and defeats the public flow. A public toggle on arbitrary existing AMIs would risk exposing persistent data.

Sources: [Packer recipe and provenance](../../platform/packer/aws/README.md), [AWS public AMI constraints](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/sharingamis-intro.html), [AWS clean-image recommendations](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/building-shared-amis.html), [regional copying](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/CopyingAMIs.html), [EBS encryption defaults](https://docs.aws.amazon.com/ebs/latest/userguide/encryption-by-default.html), [EBS encryption at launch](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/AMIEncryption.html), [Packer EBS builder](https://developer.hashicorp.com/packer/integrations/hashicorp/amazon/latest/components/builder/ebs).

## 3. Admit the exact public image through the existing catalog

**Decision.** Separate the configured deployment account from the approved AMI owner. Add an explicit official-image branch bound to the regional descriptor in the verified release, with a narrow customer stack IAM allow for the exact image ARN and publisher. The protected config pins the validated descriptor. The admin selects the official release in the catalog and runs existing validation, then uses an exact pinned resource profile.

**Rationale.** `internal/provider/ec2/provider.go` currently restricts ownership to the deployment account, rejects public AMIs and requires encrypted backing snapshots. `cmd/shiftbox/cloud_provider.go` compares publisher tags and uses the deployment account for catalog admission. `internal/release/ec2.go` binds the stored image to the installation account, and the existing demo IAM in `platform/terraform/aws/iam.tf` restricts launch source ownership. Ordinary publisher tags are unavailable to recipients. Bind the catalog manifest to the release descriptor and compare EC2-observable metadata, including exact owner, image, root device/snapshot, architecture, availability and public status. Keep the installation account association for authorization, owned instances and existing records. Reuse the authenticated admin import, disposable boot, enrollment and cleanup. Use the existing single-boot path consistently in both catalog validation and real launches once qualified, with recovery still gated. The family UI selects newest compatible by design and cannot create the existing exact non-family profile entry.

**Alternatives considered.** Removing owner checks would widen authority to unrelated images. Adopting a family-latest record would allow an install to drift from its release. Calling a privileged API from the shell would require a browser session or a new credential path.

Sources: [AWS provider validation](../../specs/002-aws-ec2-provider/quickstart.md), [EC2 sharing metadata](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/sharingamis-explicit.html), [Allowed AMIs](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-allowed-amis.html).

## 4. Use the same template and protected setup in both paths

**Decision.** Default the template to a private foundation with the normal controller disabled. CloudFormation generates independent scoped database role password secrets. The operator supplies matching DB TLS to a scoped Secrets Manager reference and passes only public DB trust to CloudFormation. Guide console users through stack outputs and local AWS CLI/SSM tunnel, and CLI users through reviewed CREATE and UPDATE change sets. Reuse the protected browser wizard and use an observed, durable activation check before reviewing controller startup.

**Rationale.** Existing setup requires database TLS, scoped secret access and a protected setup role. Reuse runtime environment names and initialization code with separate generated password references. The guided helper uses normal AWS authentication, binds to stack account/region/ID and prevents stale or ambiguous change execution. Acknowledgement is explicit. Browser and database keys remain outside stack inputs, metadata and outputs. The existing application requires a workspace owner's GitHub token for a repository clone. Operator-owned App setup is a first-workspace prerequisite separate from anonymous distribution retrieval.

**Alternatives considered.** A custom resource to generate or deliver private keys would add privileged code and logs. An unreviewed one-step startup would bypass the protected wizard. The console path requires the existing local tunnel client, not Terraform.

Sources: [Current deployment reference](../../platform/terraform/aws/README.md), [Protected setup helper](../../platform/terraform/aws/setup.sh), [AWS change sets](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/using-cfn-updating-stacks-changesets.html), [AWS pre-deployment validation](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/validate-stack-deployments.html), [Guest repository preparation](../../internal/guest/repository.go).

## 5. Scope DNS and TLS to each installation

**Decision.** Translate the existing Tailscale subnet router, restricted DNS forwarding and Route 53 private names. For the no-domain path generate and persist a unique `sb-<random>.internal` suffix. Guide authorized tailnet device registration, route acceptance, a restricted nameserver and grants. Generate an installation-specific browser signing authority and a server certificate for the existing management and wildcard names. Verify the root fingerprint through the deployment terminal and trust that root once on each operator client, then supply leaf material through protected setup. Keep the browser signing key protected and outside the runtime, with separate roles and materials for setup HTTPS, PostgreSQL TLS and guest mTLS.

**Rationale.** The router already forwards only the browser service port from the tailnet and runs a restricted DNS forwarder. Private-route operators can use their DNS forwarding/resolver and existing trusted certificate inputs. Operators need exact port and trust guidance, proofs of wildcard hostname resolution and valid HTTPS, and actionable diagnostics if routes, DNS or CA trust fail. No-domain setup depends on the one-time trust step and browser trust-store support. Validate the proposed browser CA on the target client and document renewal, expiry and retirement.

**Alternatives considered.** Public TLS or Tailscale hostname certificates would require different names or public-domain control for the existing distinct browser origins. Broad CIDRs and accepting TLS errors weaken the approved private deployment.

Sources: [Tailscale deployment baseline](../../platform/terraform/aws/README.md#optional-tailscale-access), [Tailscale restricted DNS](https://tailscale.com/docs/reference/dns-in-tailscale), [ICANN private-use reservation](https://www.icann.org/en/board-activities-and-meetings/materials/approved-resolutions-special-meeting-of-the-icann-board-29-07-2024-en), [ShiftBox certificate contract](../../documentation/architecture/certificates-and-guest-trust.md).

## 6. Qualify one candidate and promote its bytes

**Decision.** Require a protected version-tag push to enter publication. Validate supported tag syntax, fresh peeled SHA, reviewed-main ancestry and baseline checks. Use a draft with a recorded candidate payload and verify all assets before making the RC public. Keep its native runtime identity in the controller and guest artifacts across stable promotion. Store a minimal machine-readable qualification record in a reviewed, protected main commit after the public RC; keep raw evidence private. The stable annotated tag points to the RC source commit and names the RC and evidence commit. The privileged stable job reads evidence as data, verifies exact RC and artifacts against independent GitHub and AWS observations, then copies immutable assets to a new stable release without rebuild.

**Rationale.** A protected evidence commit binds four region tests and Ohio browser-E2E to one RC with no new evidence service. A separate commit allows the public draft to become immutable before tests run. A same-commit lookup alone is ambiguous with multiple RCs. Use settings that restrict tag creation to maintainers and protect updates/deletions separately. Verify settings and permissions before enabling write access. Serialize release writes and reconcile drafts using artifact identities. Refuse regression of default stable by an older rerun. Use public stable eligibility with GitHub's latest release permalink and an explicit tag lookup for RCs and pinned versions. Tag-scoped jobs with AWS OIDC use distinct scoped publisher and verify-only roles. Any promotion mismatch leaves prior stable intact.

**Alternatives considered.** Rebuilding for stable changes the evidence subject. Appending evidence to an immutable RC is unavailable. Solely relying on Actions artifacts adds expiry and public-repository visibility constraints. A mutable branch file for default stable introduces a second publication channel.

Sources: [Workflow tag filters and permissions](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax), [GitHub rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets), [Immutable releases](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases), [Release endpoints](https://docs.github.com/en/rest/releases/releases), [GitHub OIDC to AWS](https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-in-aws).

## 7. Publish a standalone documentation site

**Decision.** Build an allowlisted Jekyll Markdown site under `docs/site` through a separate Pages Actions workflow. Publish rolling stable-oriented navigation from reviewed main. Render release-provided quick-create links from verified manifest data and link to version-specific release notes and matching guides shipped in an immutable release asset, with explicit RC links. Serve the installer from releases. Use base-path-aware links and test pre-stable, stable and prerelease examples without publishing payloads.

**Rationale.** Jekyll is supported by Pages and serves text-heavy guides with a small template and pinned build. Restrict the build input to public sources and branding selected for publication. Publish availability through normal documentation changes while release resolution remains release-owned. The current main tree is architecture-only and needs the reviewed source and workflows before public launch.

**Alternatives considered.** Building a new Next.js site for static docs adds application build coupling. Exporting the repository root or current validation files risks leaking private details or misleading users.

Sources: [Pages publishing sources](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site), [Pages Actions workflow](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages), [Jekyll on Pages](https://docs.github.com/en/pages/setting-up-a-github-pages-site-with-jekyll/about-github-pages-and-jekyll).

## 8. Reuse evidence for existing product and recovery gates

**Decision.** Apply the existing V1–V14 validation register. Use the existing AWS provider quickstart for AWS equivalents of platform, enrollment transport, networking and same-installation PostgreSQL recovery checks. Run the existing UTM regression smoke separately. Require the four regional cross-account boots and hosted-template validations, one fresh Ohio console-to-IDE install, and a guided CLI rehearsal for this RC, and preserve private raw evidence with documented resource cleanup. Verify the first stable's recovery path using its own release and a disposable backup/restore target.

**Rationale.** Product contracts already specify durability, recovery, permissions and browser isolation. AWS release qualification needs evidence for their actual AWS mechanisms. Backup coverage excludes workspace disks. Irreversible migration recovery requires a matching release and archive and reviewed reconciliation. The first stable has no prior stable for a public-to-public rehearsal.

**Alternatives considered.** Treating a demo deployment or unit CI as public support evidence would miss the independent ownership, anonymity and install requirements. Reauthoring the existing gates would risk changing product behavior.

Sources: [Existing release gates](../../documentation/architecture/validation-and-engineering-defaults.md#mandatory-release-validation), [AWS validation](../002-aws-ec2-provider/quickstart.md), [backup and recovery validation](../../documentation/validation/backup-recovery.md).

## 9. Host one byte-identical template version in each supported region

**Decision.** Provision four dedicated, Terraform-managed S3 release buckets in the approved publisher account, one per supported region. Write the same template bytes under an RC/content-addressed key in each bucket. Pin the returned version ID in every object URL, record the SHA-256 and use these exact URLs for RC and stable. Keep versioning, SSE-S3, bucket-owner enforcement, ACL blocks and a release-specific policy. Anonymous read covers only versioned objects under the public launch-template prefix, with no list, write, unrelated objects or unversioned alias. Restrict Publisher IAM to intended keys and prevent deletion of referenced versions through publisher permissions and retention controls.

**Rationale.** AWS documents regional endpoints and versioned template URLs. It also notes same-region requirements for some resources, so this design makes no universal cross-region compatibility assumption. Reuse identical bytes with region-specific mapping and endpoints. Rehearse anonymous GET and cross-account CloudFormation retrieval from each region, including a region-mismatch fixture and a versioned URL with reserved characters. Validate the actual console links as well as the API. Account/organization public-access settings can override the bucket policy. Verify the designated publication context before enabling it and keep demo/customer/internal buckets out of the exception.

**Alternatives considered.** One central bucket is fewer resources, but relies on cross-region fetch behavior for the supported release. A presigned or mutable latest URL breaks durable version selection. Extra web hosting is unnecessary.

Sources: [S3 URLs and versions for CloudFormation](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/cfn-console-create-stack.html), [Quick-create URL format](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/cfn-console-create-stacks-quick-create-links.html), [S3 public access settings](https://docs.aws.amazon.com/AmazonS3/latest/userguide/access-control-block-public-access.html), [S3 version-specific policy keys](https://docs.aws.amazon.com/AmazonS3/latest/userguide/amazon-s3-policy-keys.html).

## 10. Validate, protect and diagnose public stacks

**Decision.** Run cfn-lint against all four regions, cfn-guard against explicit ShiftBox policies and CloudFormation pre-deployment validation for disposable CREATE and UPDATE change sets. Inspect validation and failed events with the current CLI and reject unexpected replacement/removal. Ship a stack policy that guards the retained encrypted EBS volume and managed secrets, require termination protection before setup proceeds, and verify retention after deleting a disposable stack. Explicitly inventory and clean retained test resources after review.

**Rationale.** Static checks cannot prove IAM, quota, regional template fetch or safe physical-resource changes. A retention policy preserves deleted or replaced storage but does not prevent an accidental outage. Keep the same AZ and physical volume on routine updates, keep normal controller stopped until setup finishes, and preserve the existing pre-migration backup and administrator recovery requirements.

Sources: [cfn-lint](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/cfn-lint.html), [CloudFormation Guard](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/cloudformation-guard.html), [Pre-deployment validation](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/validate-stack-deployments.html), [Stack policy](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/protect-stack-resources.html).
