# Release Publication Contract

**Serves** US2 and US3. See [data model](../data-model.md) for the required fields.

## Trigger, authorization and payload

- Only protected `push` events for eligible version tags can publish packages and releases. Use a broad tag pattern followed by strict parsing of the two supported forms. Before write credentials, require the intended repository and protected ref, an allowed maintainer event under the active tag rules, the event identity matching a fresh peeled tag SHA, reachable reviewed main source and passing baseline checks. Revalidate context for reruns, including the triggering actor when maintainer-only reruns are required.
- Use active tag creation restrictions and immutable update/delete controls, immutable Releases, a linked public GHCR package and separated job permissions. Verify expected controls before enabling production write access. Use restricted GitHub OIDC to an approved publisher account. Scope release environments and AWS roles by operation and authorize read-only AWS verification for promotion. Existing CI and Pages have no package-release credentials.
- Public GitHub assets are `install.sh`, `shiftbox-aws-cloudformation.yaml`, `shiftbox-aws-support.tar.gz` and `distribution-manifest.json`. Publish the template's SHA-256 in the manifest and surface it in release notes. The support archive holds region-specific catalog manifests, stack policy, stack-output setup helper and matching operator guides. Exclude deployment metadata, credentials, caches and private evidence. The template is standalone. The external manifest binds exact asset bytes, AMI/publisher IDs, and each regional S3 template URL/key/version ID and corresponding console link.
- The RC builds one full controller at an immutable digest, stamps the controller/agent compatibility version from the RC, builds and verifies the clean workspace AMI, then copies/shares the four regional AMIs. Render the standalone template once. Run cfn-lint and cfn-guard checks and verify the regional pins. Upload identical bytes to the four designated regional S3 buckets and verify each exact version, checksum, anonymous read and absence of public list/write access. Validate all four quick-create links. Public GitHub prerelease requires complete draft verification and anonymous GHCR pull.
- Keep versioned regional S3 buckets and scoped roles in internal Terraform. Use a release-only prefix, TLS-only requests, ACL blocks and bucket-owner enforcement, SSE-S3 and versioned access. Public read applies only to released template object versions. Never make an internal/demo bucket public, allow unsigned writes or use an unversioned launch URL.

## Qualification and promotion

1. Qualify the published RC in disposable AWS contexts as specified in the [validation quickstart](../quickstart.md). Approve a minimal record in `platform/manifests/qualification/<rc-tag>.json` through protected main review. Link raw evidence privately by the candidate identity.
2. A maintainer creates a protected annotated stable tag on the same peeled source commit, naming exactly one same-core RC and the reviewed evidence commit by full SHA. The stable workflow loads the record independently from that commit as data and verifies the commit is reachable from protected main.
3. Match GitHub RC ID, public prerelease status, immutable asset IDs/checksums and peeled source SHA with the evidence. Recompute downloaded checksums. Match full controller reference and platform, verify anonymous pull, and recheck all four live AMIs with exact owner, region, public launch permission, state, root snapshot and deprecation status. Retrieve all four pinned S3 object versions independently, match inspection template bytes and verify the regional launch links and hosted-template evidence. Confirm four successful region results, fresh Ohio browser IDE and gate/cleanup outcomes. Recheck release head and conditions before publishing.
4. Create the stable draft by copying identical installer, CloudFormation YAML, support archive and manifest bytes from the verified RC. Stable asset IDs are new GitHub objects, whose bytes must compare equal. The original S3 version IDs/URLs, OCI digest, AMI IDs, runtime identity and versioned docs are reused. Stable performs no template upload, AMI copy or rebuild. Publish the complete stable only after verification. Set latest explicitly for an eligible monotonic stable without allowing older reruns to move default stable backward. The GitHub Release is the canonical default and pin target.

## Restart and incomplete publication

Use a shared release mutation lock across tag runs. Persist immutable candidate provenance as each build output is staged. Reconcile the expected draft and owned staged artifacts by exact tag, commit and content before retry. Reuse verified outputs and finish missing draft uploads or sharing. A failed attempt may have exposed an individual template version, image or package digest. A candidate becomes selectable only when its complete prerelease is public. A completed identical rerun is a no-op. On incomplete or conflicting provenance, stop, preserve observations for cleanup and require a fresh RC for a new payload. Never overwrite immutable assets, broaden public AMI selection or move stable based on an unqualified draft. Classify orphaned template versions, images, snapshots and temporary build resources separately from assets that an existing release still references.

## Pages

A separate workflow builds only the approved public content, runs structure and link checks on pull requests and deploys from reviewed main with Pages-specific permissions. Pages renders the selected release's validated four regional launch links with rolling stable guidance and explicit pinned links. Update these links without touching packages, tags, releases or default stable selection. Per-release docs travel with the immutable support archive. Resolve the stable source from GitHub Releases during the separate Pages build and refresh the site through that workflow after release promotion. Before a refresh or on unavailable manifest data, link to the canonical release page rather than fabricating a launch target. Before the first stable, the site shows the available explicit RC entry only after an RC exists.
