# Qualification CloudFormation execution policy draft

This Terraform directory renders policy documents for a single disposable ShiftBox run in Ohio. It has no AWS provider, IAM resources, backend or live attachment. The GitHub deploy and cleanup identities, the four-regional AMI probes, and the workspace controller runtime have their own permissions. Keep qualification disabled pending the prerequisites below.

## Render and review

Use Terraform 1.12 or later. These are synthetic inputs for an offline review.

```sh
terraform -chdir=platform/terraform/qualification/execution init -backend=false
terraform -chdir=platform/terraform/qualification/execution test
terraform -chdir=platform/terraform/qualification/execution console \
  -var testing_account_id=111111111111 \
  -var publisher_account_id=222222222222 \
  -var run_name=sbq-123456789-2 \
  -var host_ami_id=ami-0123456789abcdef0 \
  -var router_ami_id=ami-abcdef01234567890 \
  <<'HCL' | jq -r
jsonencode(local.policy_statements)
HCL
```

The JSON map contains one identity policy string per capability. For a dry review of DNS documents, also pass synthetic `verified_vpc_id=vpc-0123456789abcdef0`, `verified_private_zone_id=Z12345ABCDE`, `verified_discovery_zone_id=Z98765ZYXWV`, `verified_namespace_id=ns-abcdefghijklmnop`, and `verified_discovery_service_ids=["srv-abcdefghijklmnop","srv-0123456789abcdef"]`. For an actual policy, obtain the account IDs using the approved AWS profiles and verify ownership of each physical ID against the stack, tags where supported, exact private suffix, and VPC association. Terraform validates the input shape. AWS ownership has to be checked separately. Review the oldest retained run and confirm none of its resources occupy the new run's role or service names.

The separate documents fit IAM's 6,144-character customer-managed policy quota and standard ten-policy attachment quota. The parent Terraform root currently takes one execution policy ARN. A later, reviewed integration must support a set of scoped managed policies or divide the work among separately controlled execution identities. Use a dedicated testing-account role. [IAM quotas](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_iam-quotas.html)

The two exact Ohio AMIs here are the Amazon Linux ECS host and optional Arm router. Read the exact host mapping from the reviewed template. Resolve and verify the router public SSM image parameter before planning, and rerun the review if it changes. The workspace AMI remains independently pinned and checked in the exact RC manifest and regional probe role. The service role permits private, IMDSv2 instance launches with the expected profiles and sizes, plus encrypted gp3 volumes up to the qualification fixture's 32 GiB. The workflow, template, and review must continue to enforce the exact per-resource mapping, network topology, and stack budget. [EC2 action and condition reference](https://docs.aws.amazon.com/service-authorization/latest/reference/list_ec2.html)

## Activation prerequisites

1. Validate the exact public RC template against the draft and its regional resource handler schemas. Review the policy documents with IAM Access Analyzer. Review a bounded IAM simulator matrix for the actual ARNs and request context, including rollback and deletion. For any create or update API that does not expose the proposed condition context, find a narrower resource or independently verified physical identifier. Prefer a reviewed template change if no bounded permission exists. CloudFormation change-set creation alone does not verify that execution will succeed. [Resource type schemas](https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/resource-type-schemas.html) · [Access Analyzer policy validation](https://docs.aws.amazon.com/IAM/latest/UserGuide/access-analyzer-policy-validation.html) · [CloudFormation change sets](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/using-cfn-updating-stacks-changesets.html)
2. Bind the deploy-side permission to the exact published, versioned S3 template URL and the run-specific stack/change set. Review every change set and its parameters, including stack name, image provenance, private network settings, phases, and run tags. A CloudFormation service role stays associated with its stack, so restrict stack operations to approved qualification identities and explicitly audit that access. The GitHub run ID and attempt are available after dispatch. At a future explicitly approved run, use the protected qualification environment's deployment approval pause to bind the approved policy to that run and attempt before authorizing execution. [CloudFormation service roles](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/using-iam-servicerole.html) · [CloudFormation IAM conditions](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/control-access-with-iam.html)
3. With `RoleBoundaryMode=external`, the template supplies the names, paths and boundary ARNs from `identity.tf`. The installer and qualification guard use `CAPABILITY_NAMED_IAM`. A separate operator must review and provision the exact host boundary before foundation. Before database, review and provision the router and task boundaries using the verified subnet, security group and secret IDs from the run. Limit each boundary to that role's workload. Review the initial trust in the immutable RC because IAM cannot constrain the trust document content. Trust-policy updates and boundary changes are outside the execution role. The two allowed AWS managed policy attachments are specific to the host and router roles. Confirm any ECS service-linked role separately. [CloudFormation IAM role resource](https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-resource-iam-role.html) · [IAM action and condition reference](https://docs.aws.amazon.com/service-authorization/latest/reference/list_iam.html) · [Permissions boundaries](https://docs.aws.amazon.com/IAM/latest/UserGuide/access_policies_boundaries.html)
4. External boundary mode gives the four retained database secrets exact run-specific names and omits the managed setup-operator policy. The operator identity owns setup access. This execution role has no ECS Exec channels, `ecs:RunTask`, SSM session start, application workspace orchestration, or secret-value read grants. Database rotation, data migration and deleting retained storage require separate operator or qualified cleanup actions. [ECS action and condition reference](https://docs.aws.amazon.com/service-authorization/latest/reference/list_ecs.html) · [Secrets Manager action and condition reference](https://docs.aws.amazon.com/service-authorization/latest/reference/list_secretsmanager.html)
5. Foundation creates the VPC. `dns-zones` adds the application zone and the Cloud Map namespace. `dns-services` adds the two discovery services. The `database` change set adds the six CNAMEs and starts protected setup. Verify exact DNS suffixes, VPC association, namespace, run tags and service IDs at the handoffs. The automated workflow previews `dns-zones` and discards it. The separately scoped staffed path creates and tags the DNS resources in the public deployment lane. AWS assigns IDs at creation and separately authorizes Cloud Map tagging. This draft keeps tagging and service mutations scoped to individually verified IDs. Route 53 record edits and zone deletion also target individually verified IDs. Confirm the Cloud Map forwarded-call context and the actual dependent calls before any restricted-role execution beyond foundation. [Route 53 condition keys](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/specifying-conditions-route53.html) · [Record set conditions](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/resource-record-sets-permissions.html) · [Cloud Map API dependencies](https://docs.aws.amazon.com/cloud-map/latest/dg/cloud-map-api-permissions-ref.html)
6. Confirm clean rollback and deletion for the disposable stack and independently verify removal of intentionally retained disk and database secrets through the cleanup role. Root EBS volumes must remain delete-on-termination. Verify that role/profile naming, AWS tag-on-create propagation, EC2 network and instance API request contexts, and CloudFormation ECS handler arguments match the scoped grants before assuming those operations are available. Confirm service trust, grant boundaries, service-linked role dependencies, and all AWS policy checks with the exact RC before approving a paid run.

The Ohio public registry schemas for the 28 resource types in the current source expose follow-up checks that a clean Access Analyzer result cannot cover.

- The Secrets Manager resource read handler declares `secretsmanager:GetSecretValue`. This draft leaves it out. Verify whether create, change-set validation and stabilization invoke that handler for the exact template. If they do, move secret creation and retention to a separately approved operator step and pass verified ARNs, or have the security review approve narrowly scoped value reads for the precise disposable secret IDs. Keep generic secret reads out of the role.
- The ECS service schema declares deployment-history reads during create and update, including `ecs:ListServiceDeployments` and `ecs:DescribeServiceDeployments`. The SSM document schema declares `ssm:GetDocument`. Confirm use and add only the exact service, deployment and setup document ARNs if the corresponding handler needs them.
- The encrypted EBS volume resource schema declares KMS grant and data-key operations for supported configurations. Verify the exact default EBS key and handler behavior. A customer-managed key requires a separately reviewed key policy and exact key scope.
- The general network handlers declare additional operations for optional configurations, such as Elastic IP transfer, VPN gateways, alternate VPC or subnet configurations, tag removal and log delivery. Confirm which are invoked even when the corresponding property is absent, and scope any observed requirement to the reviewed run. The draft keeps those alternative operations out.

A schema's permission inventory covers its supported property combinations and cannot establish which calls the exact run requires. Qualify the material handler paths before attaching this policy for execution.

The packaged-template fixture uses these generated policies to check role and profile names, boundaries, kept secret names, and the DNS phase and record restrictions without AWS. An exact public RC, independent runtime boundaries, a live execution policy attachment and the staffed role remain separate activation prerequisites.
